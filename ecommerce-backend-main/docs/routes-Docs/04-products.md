# products.js — Product Catalog (Explained for Rebuilding)

---

## 1. What this file is

CRUD (Create, Read, Update, Delete) for products. Anyone can **read**; only admins can **write**.

| Operation | URL | Auth |
|---|---|---|
| List / search | `GET /products` (`?search=text`) | Public |
| One product | `GET /products/{id}` | Public |
| Create | `POST /products` | Admin |
| Edit | `PUT /products/{id}` | Admin |
| Delete | `DELETE /products/{id}` | Admin |

## 2. Data model

**Product**

| Field | Type | Rules |
|---|---|---|
| id | UUID | generated by the DB |
| name | string | required, trimmed |
| image | string (URL/path) | required, trimmed |
| priceCents | integer | ≥ 0 |
| keywords | JSON array of strings | default `[]`, used by search |
| rating | JSON `{ stars, count }` | default `{stars: 0, count: 0}` |
| stock | integer | 0 … 100000 |
| description | string | ≤ 2000 chars, default `''` |
| createdAt / updatedAt | timestamps | automatic |

## 3. Constants and helper at the top

```js
const UUID_PATTERN = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
const MAX_DESCRIPTION_LENGTH = 2000;
const MAX_STOCK = 100000;
```

- `UUID_PATTERN` checks that a string looks like a UUID (8-4-4-4-12 hex digits, case-insensitive).
- The limits protect the database and UI from absurd values.

```js
function cleanKeywords(keywords) {
  if (Array.isArray(keywords)) return keywords.map(k => String(k).trim()).filter(Boolean);
  if (typeof keywords === 'string') return keywords.split(',').map(k => k.trim()).filter(Boolean);
  return null;
}
```

Accepts `["a","b"]` or `"a, b"`; trims each item; removes empty ones; returns `null` for anything else (= invalid). `filter(Boolean)` drops empty strings.

## 4. GET /products — list and search

```js
products = await Product.findAll();
if (search) {
  const q = search.toLowerCase();
  products = products.filter(p =>
    p.name.toLowerCase().includes(q) ||
    p.keywords.some(k => k.toLowerCase().includes(q)));
}
res.json(products);
```

Behavior:
- No `search` → all products (sold-out included; the frontend can check `stock === 0`).
- With `search` → case-insensitive "contains" on the name **or** any keyword.

Rebuild in SQL: `WHERE LOWER(name) LIKE '%q%'` plus a keywords table or a JSON/array search (`ANY`, `JSON_CONTAINS`, `@>`). For big catalogs use full-text search (PostgreSQL `tsvector`, Elasticsearch, Meilisearch, Algolia).

## 5. GET /products/{id}

```js
if (!UUID_PATTERN.test(req.params.id)) return res.status(404).json({ error: 'Product not found' });
const product = await Product.findByPk(req.params.id);
if (!product) return res.status(404)...;
res.json(product);
```

The UUID check exists because PostgreSQL throws an error when asked to compare a UUID column with `"hello"`. By answering 404 early the server never reaches the database with bad input. In other stacks the framework often does this (typed route parameter `{id:guid}` in ASP.NET, `UUID` type in FastAPI).

## 6. POST /products — create (admin)

Middleware: `requireAuth, requireAdmin` (login first, then role check).

Validation order and messages:

| # | Check | Error (400) |
|---|---|---|
| 1 | `name` is a non-empty string | Name is required |
| 2 | `image` is a non-empty string | Image is required |
| 3 | `priceCents` is an integer ≥ 0 | priceCents must be a whole number, 0 or more |
| 4 | `stock` is an integer 0…100000 | Stock must be a whole number from 0 to 100000 |
| 5 | `description` (if given) is a string | description must be text |
| 6 | `description` ≤ 2000 chars | Description can be at most 2000 characters |

Then:

```js
Product.create({
  name: name.trim(), image: image.trim(), priceCents,
  keywords: cleanKeywords(keywords) ?? [],
  rating: rating ?? { stars: 0, count: 0 },
  stock,
  description: (description ?? '').trim()
});
```

`??` = "if left side is null/undefined use right side". Response: `201` + the product.

Note: unlike `keywords`, an invalid `keywords` on create silently becomes `[]`; on edit it returns 400. Decide which behavior you want when you rebuild.

## 7. PUT /products/{id} — partial edit (admin)

Pattern: *only change the fields that were sent*.

```
product = find(id) or 404
if body.name      !== undefined: validate non-empty string, then product.name = trimmed
if body.image     !== undefined: validate non-empty string
if body.priceCents!== undefined: validate integer >= 0
if body.keywords  !== undefined: cleanKeywords or 400
if body.rating    !== undefined: assign as is   (no validation!)
if body.stock     !== undefined: validate integer 0..MAX_STOCK
if body.description !== undefined: validate string and length
save()
return product
```

This is "PATCH semantics" implemented under PUT. A strict REST rebuild would use `PATCH` for partial and `PUT` for full replacement.

Weak points to fix in a rebuild: `rating` is unvalidated (check `stars` 0–5 and `count` integer ≥ 0) and the UUID pattern is not checked here.

## 8. DELETE /products/{id} — remove (admin)

```js
await CartItem.destroy({ where: { productId: product.id } });
await product.destroy();
res.status(204).send();
```

1. Find the product (404 if missing).
2. Remove it from every user's cart first. Carts reference products; deleting the product first could violate a foreign key or leave broken rows.
3. Delete the product.
4. `204 No Content`.

Old orders keep the `productId` inside their JSON lines. The admin orders endpoint reports `product: null` for them. Alternatives: **soft delete** (`deletedAt` / `isActive = false`) so history always has a product to show. This is better practice.

## 9. Pseudocode summary

```
GET    /products?search     -> all products, optionally filtered by name/keywords
GET    /products/{id}       -> 404 if bad id or missing
POST   /products (admin)    -> validate -> insert -> 201
PUT    /products/{id} (admin) -> partial validate+update -> 200
DELETE /products/{id} (admin) -> remove from carts -> delete -> 204
```

## 10. Rebuild notes

- **Admin check:** a role claim in the token/session, verified on the server on every request.
- **Images:** here `image` is just a string path. For uploads use cloud storage (S3, Cloudinary) and save the URL.
- **Ratings:** `{stars, count}` is a denormalized summary; a bigger project would have a `reviews` table and compute it.
- **Validation libraries:** Zod/Joi (JS), Pydantic (Python), FluentValidation (C#), Bean Validation (Java). They replace the long `if` chains.
- **Pagination:** add `?page=1&limit=20` for big catalogs.
