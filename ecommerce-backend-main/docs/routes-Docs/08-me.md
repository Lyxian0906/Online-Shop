# me.js — Current User Endpoint (Explained for Rebuilding)

---

## 1. What this file is

The shortest file of the project, but the one the frontend calls first after login. It answers: **"Who am I and what am I allowed to do?"**

| Item | Value |
|---|---|
| URL | `GET /me` |
| Auth | Required |
| Response | `{ "id": "...", "email": "...", "role": "customer" or "admin" }` |

## 2. The whole code

```js
router.get('/', requireAuth, (req, res) => {
  res.json(req.user); // { id, email, role }
});
```

All the work happens inside `requireAuth` (in `middleware/auth.js`). It:

1. Reads the credentials from the request (cookie, `Authorization: Bearer <token>` header, or a session).
2. Verifies them (JWT signature, session store, or the identity provider).
3. Loads or decodes the user and puts `{ id, email, role }` into `req.user`.
4. If anything fails → responds `401` and stops.

Then this handler just returns `req.user`. There is no `async` and no database query in this file.

The comment at the bottom explains the purpose: the frontend calls it after login to learn the user and whether they are an admin.

## 3. Frontend flow

```
1. User logs in (email + password / social login).
2. Frontend calls GET /me.
   - 401  -> show login page
   - 200  -> save the user in app state
3. if user.role == "admin": show admin menu and pages
   else: show the normal store
4. Show user.email in the header
```

## 4. Why it exists

- The frontend cannot safely read the role from a client-side token and trust it; asking the server is the source of truth.
- It restores the session after a page refresh.
- It is the single place the UI learns the user's id (needed e.g. to know whether a chat message is "mine").

**Security reminder:** hiding admin buttons is only cosmetic. Every admin endpoint must check the role again on the server (`requireAdmin`).

## 5. What `requireAuth` and `requireAdmin` must do (you must build them)

These two functions are *not* in the uploaded files, but every route depends on them:

```js
// requireAuth: verify login and set req.user
async function requireAuth(req, res, next) {
  const user = await verifyCredentials(req);       // your auth method
  if (!user) return res.status(401).json({ error: 'Not logged in' });
  req.user = { id: user.id, email: user.email, role: user.role };
  next();
}

// requireAdmin: must run after requireAuth
function requireAdmin(req, res, next) {
  if (req.user?.role !== 'admin') return res.status(403).json({ error: 'Admins only' });
  next();
}
```

Where the `role` comes from: the `Profile` table (the admin panel loads `Profile.id` and `Profile.email`), so a profile likely has `id`, `email`, `role`.

## 6. Rebuild notes

| Your new stack | Equivalent |
|---|---|
| FastAPI | `Depends(get_current_user)` returning the user model |
| ASP.NET | `[Authorize]` + `User.Claims` |
| Spring Boot | `@AuthenticationPrincipal` |
| Next.js | server session helper (NextAuth / Clerk / Supabase `getUser()`) |
| Firebase / Supabase | `auth.currentUser` / `supabase.auth.getUser()` + a `profiles` row for role |

- Never include password hashes or secrets in the response.
- You can add fields (`name`, `avatarUrl`) later; the frontend should ignore unknown fields.
